# 小红书公开视频基础支持设计

> **状态**：已批准  
> **决策日期**：2026-08-11

## 一、产品决策

知录把小红书加入正式支持的公开媒体平台范围。第一阶段只承诺公开可访问的视频笔记进入现有知识工作台，不把能力扩展成小红书采集器或账号工具。

完成标准：用户粘贴受支持的小红书公开视频页面链接后，系统能够沿用现有解析、AI 转写、总结和本地档案链路，并稳定显示视频标题、作者昵称、封面、时长和“小红书”平台名称。

## 二、问题与证据

当前通用 yt-dlp 兜底已经能够解析小红书公开视频、视频格式和封面，但 yt-dlp 的 `XiaoHongShuIE` 只导出 `uploader_id`，没有把公开页面中的 `note.user.nickname` 导出为 `uploader`。因此知录的通用元数据转换只能回退成“未知作者”。

平台字段已经被 yt-dlp 规范化为 `xiaohongshu`，但前端的平台名称转换存在两份实现，且都缺少 `xiaohongshu → 小红书` 映射，所以列表和详情显示了内部平台键。

## 三、方案比较

### 方案 A：只补前端平台名称

改动最小，但作者仍然错误，不能构成正式平台支持，不采用。

### 方案 B：薄平台适配器补齐公开作者信息

在默认 yt-dlp Adapter 之前注册小红书公开视频 Adapter。视频、格式、封面和时长继续复用 yt-dlp；作者缺失时，从同一公开页面的 `window.__INITIAL_STATE__` 中读取 `note.user.nickname`。前端统一复用一份平台名称转换。

这是当前采用方案：复用成熟解析能力，只补上游没有导出的稳定业务字段，改动范围和后续维护成本可控。

### 方案 C：完全自研小红书解析器

自行维护页面结构、视频流、图片和格式提取，控制力更高，但会重复 yt-dlp 已有能力，并显著扩大平台适配和风控维护范围。当前没有需求支撑，不采用。

## 四、架构与数据流

```text
公开小红书视频页面 URL
→ POST /api/parse
→ XiaohongshuVideoSourceAdapter
→ yt-dlp 获取视频元数据、格式、封面和时长
→ 作者为空时读取公开页面 INITIAL_STATE
→ 提取 note.user.nickname
→ 统一返回 platform = "xiaohongshu"
→ library_service 写入现有 SQLite 档案
→ 前端共享 getPlatformLabel() 显示“小红书”
```

平台识别和作者补齐属于后端输入源层；前端只负责把稳定的平台键转换为用户可读名称，不在组件内猜测作者或修补后端数据。

## 五、支持边界

当前支持：

- `xiaohongshu.com/explore/<note_id>` 公开视频页面；
- `xiaohongshu.com/discovery/item/<note_id>` 公开视频页面；
- 无平台字幕时，用户手动触发现有 ASR 转写；
- 新解析或重新解析后写入作者昵称和平台键。

当前不支持：

- 登录后才能访问、私密、付费、删除或受限内容；
- 图文笔记的图片批量提取；
- 账号主页、收藏、评论、搜索和批量采集；
- 自动登录、自动获取 Cookie、绕过验证码或平台风控；
- 对旧档案静默联网回填。旧记录需要用户重新解析后更新。

页面结构变化导致作者补取失败时，视频解析仍可返回，作者回退为“未知作者”，不能因辅助字段失败阻断主流程。

## 六、实现范围

1. 新增小红书 URL 识别和公开作者补齐服务，并注册到媒体输入源分派层。
2. 为 URL 识别、作者提取、作者补取失败回退和 Adapter 分派增加后端测试。
3. 将平台名称转换收敛到 `frontend/lib/library-display.ts`，删除详情组件中的重复实现。
4. 增加“小红书”平台显示测试，并检查最近档案与详情卡片两个使用位置。
5. 实现和验证完成后，更新 `docs/project-context.md` 与小红书平台架构文档，记录已落地能力和长期边界。

## 七、验证

- 后端单元测试覆盖小红书 URL、作者昵称提取、失败降级和 ParseResponse 字段。
- 前端 helper 测试覆盖 `xiaohongshu → 小红书`。
- 前端生产构建或相关浏览器测试确认列表和详情共用同一平台名称。
- 使用公开小红书视频页面做一次最小真实解析，确认标题、作者、平台、封面和时长均返回；不下载媒体、不启动 ASR。
