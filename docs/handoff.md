## 2. 自审结论与本轮收敛

方向可实施，但不能用前端循环调用现有接口冒充可靠队列。必须解决以下直接影响并行处理的问题：

| 现有证据 | 实施要求 |
| --- | --- |
| `scripts/extract-douyin-media.mjs` 用固定目录启动 `launchPersistentContext`；解析与下载均调用它 | 所有浏览器调用共用一个互斥入口；不能解析 1 个、下载 1 个后同时占用同一 Profile |
| `asr_service.transcribe_media_audio` 内部串联下载、识别、校对，并删除临时媒体 | 拆分阶段、持久保存检查点；识别结束就释放识别名额，网络校对不占用 GPU 名额 |
| `use-transcribe-workflow.ts` 在浏览器收到转写结果后才触发总结 | 自动接续迁到后端；关网页不丢下一步 |
| `main.py` 多个写库异常仅记录日志，转写/总结写回找不到记录时可能静默返回 | 新任务只有结果持久化成功后才完成；保存失败必须可见且可重试保存 |
| `library_service.py` 多处读取整份 JSON、修改后整份覆盖 | 在短写事务中读取最新值再合并；不允许后台总结覆盖同期手动摘录 |
| 相同内容可从短链/长链、多标签页、单条/批量入口进入 | 提交幂等 + 内容身份去重 + 同一内容生成任务互斥，不能只在输入框去重 |
| DeepSeek、抖音已有内部重试 | 不再叠加多层整任务重试；AI 返回不明时不宣称恰好执行一次 |
| `scripts/launch-site.ps1` 默认 `--reload` | 普通启动去掉自动重载；任务调度只允许一个执行进程，重启要恢复检查点 |
| SenseVoice 有 GPU 模型缓存 | 识别并发 1 也不代表显存自动释放；切换引擎要释放不用的模型，禁止两种模型无上限驻留 |

本次不做：Redis/Celery、多机调度、多浏览器 Profile、主页采集、云转写、用户可调并发面板、批量文件导出、自动保存全部原视频、任务优先级编辑、强杀当前单条任务、模型性能优化工程。

## 3. 功能合同与处理策略

### 3.1 输入、容量和目标

1. 单次接受 1～49 条去重后的有效视频链接；超过 49 明确返回超限，不截断。设置有限原文长度（建议 64 KiB），前后端一致。
2. 为兑现当前小批量范围，本机全局未结束任务也最多 49 条；并发提交在数据库事务内判断容量，不能各自检查后超额入队。失败/完成/取消不占容量，重试需重新检查。
3. 支持多行分享文案和一行多个 URL；前端展示有效、重复、无效项，后端重复校验。保留 B 站分 P、定位参数的现有语义，不能靠删除全部 query 去重。
4. 页面提供两个目标：`parse_only`（仅提取现成内容）和 `analyze`（生成全文与总结，默认）。内部单条适配还需 `transcribe_only`、`summarize_only`，无需把这两个新增为批量页面选项。
5. `analyze`：已有可用全文则跳过下载/ASR/校对并总结；只有 shownotes 时仍需全文转写；已有完整总结则复用。复用必须检查真实文本和非占位状态，不能仅看 `has_transcript`。
6. 批量默认补齐缺失结果，不主动覆盖历史、不批量强制重转写。明确选择引擎的现有单条重转写行为仍保留。
7. 本批次存储目标、引擎、通用校对设置快照；视频标题、作者、shownotes 等逐条读取。批量弹窗不把特定人物或节目语境套给所有视频。
8. 无效项由用户移除后提交有效项；预检查不执行真实媒体解析或调用 AI。

### 3.2 资源与流水线

逻辑阶段：`parse → download → recognize → correct → summarize → done`，按目标和已有结果跳过不需要的阶段。

| 资源 | 第一版上限 | 覆盖范围 |
| --- | ---: | --- |
| 抖音浏览器 | 1 | 页面解析、转写媒体获取、手动下载、封面补取等所有 `_run_browser_helper` 调用 |
| 非抖音元数据解析 | 2 | 使用现有 Adapter |
| 媒体下载 | 2 | 所有任务临时媒体下载和现有手动媒体下载；抖音还需浏览器互斥 |
| 本地识别 | 1 | Whisper、SenseVoice 共用，同样涵盖单条入口 |
| AI 阶段工作槽 | 2 | 校对、总结；防止向线程池提交无限量等待请求 |
| DeepSeek 实际 HTTP 请求 | 2 | 在公共客户端统一控制，包含校对分块、shownotes 上下文、总结及现有 QA |

- 视频 A 识别时允许 B 下载；A 校对时允许 B 识别、C 下载。用合成任务验证真实重叠，不能只看界面同时出现多个“处理中”。
- 使用有界阶段工作池/队列，数据库为任务事实来源；内存队列只装有空闲名额的工作，不提交几十个阻塞线程。
- 浏览器互斥应落在 Python helper 调用边界；调度器把抖音解析/下载视为共用浏览器资源，公平交替处理就绪阶段，避免先解析完 49 条才开始第一条下载。
- 对需要多个资源的操作规定统一获取顺序；不持有 GPU 等待下载或网络，不对同一资源重复获取非可重入锁。把资源边界写清并用测试覆盖嵌套路径。
- 阶段完成释放资源后再调度下一阶段；DB 事务中严禁执行网络、子进程、模型识别或等待资源。
- 预下载设背压：建议最多保留 2 个完整媒体等待识别，另允许最多 2 个下载中。达到上限停止领取下载阶段，不能把 49 个大视频全下到本地。
- 保留现有文件大小限制，下载前检查可用空间，磁盘不足将该阶段置为可解释失败，其他无需下载的任务可继续。
- 媒体地址可能过期：只持久保存来源身份和受控本地路径；开始下载时按现有 Adapter 获取/刷新地址，最多一次因过期刷新重试，不长期依赖解析阶段的直链。

### 3.3 状态、失败和取消

- 分开存储 `status` 与 `stage`：状态至少 `queued/running/waiting_retry/succeeded/failed/cancelled`；阶段决定“等待转写”“下载中”等文案。
- `waiting_retry` 必须有 `next_attempt_at` 和原因；普通处理失败不能无限自动循环。
- 复用成功和自动校对降级可用 `result_kind`、结构化 warning 表达，不额外制造多套状态枚举。
- 校对失败保留原始稿并显示降级信息；沿用现有总结 fallback 合同，但本地 fallback 不标成“AI 总结成功”，允许用户主动重试总结阶段。
- 网络层沿用已有有界重试；队列第一版不再自动重跑失败的整个 AI/解析阶段。自动等待仅用于明确的本地额度恢复，媒体过期仅一次刷新。错误为配置缺失/鉴权失败时直接展示原因。
- 第一版“取消”只取消未执行阶段：没有其他批次需要此任务时，正在执行的阶段可以完成并保存已有结果，但不得继续下一阶段；界面显示“将在当前步骤结束后停止”。取消不是删除已生成内容。
- 同一执行任务被多个批次复用时，取消只取消当前批次的关联；其他批次仍需结果则继续执行。只有最后一个有效关联取消才停止后续阶段，不能让一个批次取消另一个批次的工作。
- 取消、领取、重试都用条件更新保证并发一致；点击重试两次不能启动两份工作。
- 处理过程中删除同一内容、清空内容库由后端返回 409 并解释仍有任务；前端保留原位置。避免删除后旧 worker 又把内容写回来。无需新增复杂软删除系统。

## 4. 后端模块与修改方法

### 4.1 新增最小任务层

建议新增以下文件，沿用仓库 Python 命名与测试模式，不再增加一套平行平台实现：

| 文件 | 职责与要求 |
| --- | --- |
| `backend/app/services/task_store.py` | 任务表初始化、事务式创建/领取/完成、检查点、幂等和恢复查询；不执行模型或网络 |
| `backend/app/services/task_runner.py` | 生命周期、单调度实例、资源名额、阶段执行、取消/恢复；只编排已有服务 |
| `backend/app/services/processing_service.py` | 从 `main.py` 提取可复用的解析、上下文补齐、阶段调用与结果组装，供任务层和旧 API 共用 |
| `backend/app/routers/tasks.py` | 新任务/批次 HTTP 接口，保持 `main.py` 简洁 |

资源控制可先作为 `task_runner` 的独立小类；若公共 DeepSeek/helper 引用造成循环依赖，再拆 `processing_resources.py`，不要为凑文件提前分层。

同一 SQLite 文件新增 `processing_batches`、`processing_tasks`、`processing_batch_items`；沿用原内容库作为最终内容的唯一权威来源。

- 批次：`id`、`client_request_id`（唯一）、请求内容哈希、目标/设置快照、创建时间。
- 任务：`id`、提交序号、原始/规范化 URL、`content_key`、目标/设置、`status`、`stage`、尝试次数、`next_attempt_at`、错误代码/安全信息、当前执行 token、检查点、关联内容 ID、时间戳。
- 批次关联：批次 ID、任务 ID、输入位置、关联取消时间；批次内任务关联唯一。批次行状态由关联取消状态优先、否则由执行任务状态派生，不复制一份执行状态。
- 重复项：同一次请求直接折叠；不同批次发现已有相同目标和设置的活跃任务时，通过关联复用同一执行任务，不复制执行。关联本身不额外占容量。
- 同一内容但目标/设置不同：等待已有生成任务结束后重新检查已完成结果，再执行缺失动作；识别完成前不能并发生成基于旧稿的总结。
- `content_key` 至少包含平台、稳定视频 ID 和需保留的分 P 维度。入队先按规范化 URL 去重，解析得到稳定 ID 后在事务内合并别名/关联；碰撞任务不得进入下游双重执行。
- 不以数据库内首次拿到的短链永久充当唯一内容身份；也不大范围改造历史主键。新增任务身份映射到既有 library 记录，保证写回同一对象。
- 批次统计从关联和任务状态派生；前端不自己递增“完成数”。终态统计包含取消，复用项不重复计入全局运行数。

### 4.2 拆分 ASR，保留旧合同

主要文件：`asr_service.py`、`sensevoice_service.py`、`transcript_correction_service.py`、`shownotes_context_service.py`、`douyin_service.py`。

从 `transcribe_media_audio` 提取能独立测试的三个阶段函数，名称可按现有风格微调：

1. `prepare_transcription_media(...)`：在 `backend/data/tasks/<task_id>/` 下获取媒体，写临时文件后原子更名；返回文件描述，不返回包含 Cookie 的持久配置。
2. `recognize_transcription_media(...)`：仅运行引擎、片段整理和原始稿构建，返回原始结果与耗时/引擎元数据；成功先保存原始稿检查点，再释放识别名额。
3. `finalize_transcription(...)`：从原始稿和设置快照运行上下文合并、校对、双稿组装，复用现有规则；不能重新下载或识别。

- 保留 `transcribe_media_audio` 对现有调用方/测试的兼容入口，由它组合上述函数，不复制核心算法。
- 小宇宙 shownotes 上下文若需要 AI，转入有名额的网络阶段；第一版可顺序处理，不为保留原来的内部并行再增加线程。保持最终上下文质量合同。
- 复用当前模型回退与中性 Whisper 解码；不修改识别参数、提示词策略、片段规则或默认引擎。
- SenseVoice 缓存和 Whisper 实例的持有期必须明确；引擎切换时释放不再使用的 GPU 模型，确认实际实现后决定是否需专用清理函数。不要顺便实现新的长期模型缓存。
- 任务媒体只能删除在受控 tasks 根目录内验证过的路径；`.part` 不算完成；进程重启后检查存在性/长度，缺失时退回下载阶段。
- 原始稿成功持久化后可删除媒体，后续校对重试复用原始稿；下载成功但识别失败时保留可重试媒体并设置有限保留期（建议 24 小时），到期清理且标记重新下载。清理只在启动/阶段结束触发，不另做常驻服务。

### 4.3 结果写库：处理成功不等于保存成功

主要文件：`library_service.py`、`task_store.py`。

- 所有内容 JSON 的读-改-写，必须在同一短写事务内读最新值后更新。重点覆盖 `upsert_library_item`、`update_transcript_for_source_url`、`update_summary_for_source_url`、`update_note_draft_for_source_url`。
- 可用 `BEGIN IMMEDIATE` 串行化写事务、设置有限 busy timeout；每个线程独立连接。WAL 可按现有测试方式启用，但不能用 WAL 代替原子读改写。
- 解析刷新只合并元数据，不抹掉已有转写、总结、摘录；保留小红书当前刷新语义。
- 新任务路径不吞写库异常，目标不存在必须显式失败；任务 `succeeded` 的前提是库记录可回读。
- 在同一数据库事务内完成“当前结果写库 + 检查点/阶段推进”，给既有更新函数增加内部 connection 参数或提取连接级 helper；禁止二次提交让旧阶段重放覆盖新结果。
- 外部调用结果先作为阶段检查点保存；数据库临时故障优先重试保存，不能直接重复付费生成。
- 总结保存携带输入文本摘要/版本；写回时核对当前文本仍匹配。若用户切换转写版本，旧总结不能覆盖新版本结果，应回到等待总结或显示结果过期。
- 删除/清空的“是否仍有任务”检查与实际删除放在同一写事务；不能在事务外先检查后删除，让新任务在间隙进入。
- 所有迟到 worker 结果校验执行 token 和当前阶段，不能覆盖取消后重试产生的新执行结果。
- 转写重放不能重复清空后来生成的总结；手动摘录和不同字段的并行更新不能丢失。

### 4.4 生命周期与恢复

主要文件：`main.py` 的 FastAPI 生命周期、`scripts/launch-site.ps1`、必要的启动说明。

- 应用 lifespan 启动一次调度器并初始化表；不要在模块 import、每次请求、每次查询时创建 worker。
- 普通启动器去掉 `--reload`，开发者手动 reload 保留为开发用法。第一版只支持一个执行进程。
- 增加进程级独占执行锁（使用项目已有能力或标准库文件锁）；第二个实例无法拿锁时清晰拒绝启动执行服务，不悄悄形成双 worker。只写“请勿多开”不算防护。
- 停止时不再领取任务，有界等待当前阶段；处理 helper 超时/退出时必须清理本次创建的 Node/浏览器子进程，不关闭用户日常浏览器。
- Python 线程中的原生识别不能靠 Future 超时强行终止。超时后若底层仍在运行，必须继续占用识别名额；不得启动第二次识别。应用重启时旧执行进程实际退出、释放执行锁后才能恢复；如无法做到有界退出，明确报告此限制，不伪造已停止。
- 完整后端进程退出后依检查点恢复；不能只因 running 已超过固定几分钟就重复领取仍活着的长 ASR 任务。识别执行过程不支持断点，只有该阶段需重跑。
- 重启前已经保存的解析、媒体、原始稿、最终稿、总结按检查点复用。
- **付费请求发送后、响应保存前崩溃存在不可消除的不确定窗口。** 此类 AI 阶段标记 `AI_RESULT_UNCERTAIN` 为失败，保留前置结果，等待用户主动重试；不要自动再次付费，也不要承诺 exactly-once。

### 4.5 接口与旧入口兼容

新增 Pydantic 类型在 `schemas.py`，前端镜像到 `lib/types.ts`：

| 接口 | 合同 |
| --- | --- |
| `POST /api/task-batches` | `client_request_id`、链接数组、目标与设置；快速返回 202，包含批次和任务关联、去重信息，不等待真实媒体处理 |
| `GET /api/task-batches` | 最近批次和全局活跃统计，有限返回，供任务入口恢复 |
| `GET /api/task-batches/{id}` | 批次、任务行及统计同一响应快照；不返回全文/完整总结/本地文件路径 |
| `GET /api/tasks/{id}` | 单项状态、错误、阶段和可用结果引用 |
| `POST /api/tasks/{id}/retry` | 请求携带 `batch_id`，恢复该关联并重试最早未完成阶段，已有工作运行则复用，保留成功检查点 |
| `POST /api/tasks/{id}/cancel` | 请求携带 `batch_id`，幂等取消当前关联；最后一个有效关联取消才停止执行任务的后续阶段 |

- 同一个 `client_request_id` + 相同内容重复提交返回同一批次；不同内容复用此 key 返回 409。网络超时后前端必须携带原 key 重试。
- 无效输入返回逐项校验错误，不创建半个批次；容量不足原子拒绝，不静默接受部分。
- 批量重试可以调用同一重试服务并逐项返回结果，不另写不受限制的批量 worker。
- 新前端单条生成也提交同一任务服务，以一个任务的批次或等价内部调用执行，按原有意图决定目标，不能改变当前单条默认行为。
- 原 `/api/parse`、`/api/transcribe`、`/api/summarize` 保留原请求/响应合同；可作为提交同一任务并等待结果的兼容包装。HTTP 请求断开不取消已创建任务，包装层不能自行重做下一阶段。
- 内部 worker 直接调服务函数，禁止向自身 HTTP API 发请求，禁止路由和任务层递归调用。
- 现有手动下载仍走其文件响应合同，但接入同一下载与浏览器资源限制；封面补取等隐含浏览器路径也必须走共同互斥。
- URL 公网校验、平台 Adapter 顺序、错误 `error_code/message` 及原有 API 验证不能被任务接口绕过。

### 4.6 频控与重试计数

主要文件：`main.py`、`rate_limit_service.py`、`backend/.env.example`、`docs/configuration.md`。

- 将额度检查提取为不依赖 HTTP Request 的服务方法，任务保存提交时得到的 client key，不伪造 Request、不绕过额度。
- 实际执行新阶段时才记一次使用；同一提交幂等重试、查询、缓存复用和 worker 领取不重复扣额度。数据库内检查并递增必须原子化。
- 代码默认解析/转写/总结额度统一建议 50 次/小时，以容纳一次最大批次；QA 不变。已有本地环境覆盖值保留，不擅自覆盖 `.env`。
- 现有实例若显式配置更低额度，达到额度后进入 `waiting_retry`，记录恢复时间，不标永久失败，不忙轮询；用户可看到“等待额度恢复”。
- 额度等待不占浏览器、下载、GPU、AI 工作槽；重启后保留恢复时间。
- DeepSeek 429 等仍由现有客户端的有限策略处理，耗尽后该阶段失败；不要套一个无限队列重试再重复内部 3 次请求。

## 6. 实施顺序与阶段出口

按以下顺序推进；每阶段完成后给出简短证据，非用户要求审批无需逐步停下来，但不能跳过后端可靠性先宣称功能完成。

1. **任务存储与调度骨架**：新增表、状态转换、幂等、全局容量和资源限制，用合成阶段 runner 完成 30 条；证明不同阶段重叠、同资源不超限。
2. **真实服务拆分**：拆 ASR 三阶段、接入现有 Adapter 和 DeepSeek；先用注入 fake 测试，保留原单条合同。
3. **持久化与并发写回**：原子检查点、事务式 JSON 合并、文本版本检查、内容身份去重；完成失败保存/重复领取/取消竞争测试。
4. **生命周期与兼容路径**：单进程执行锁、启动器、恢复、额度、手动下载/旧 API/封面隐含路径共同限流；不能只保证新批量 API。
5. **批量界面**：入口、弹窗、批次列表、进度、单条回看；把前端续接与 sessionStorage 任务控制迁走。
6. **集成与交付**：相关后端测试、helper tests、前端构建；有权限时运行 mock E2E；更新代码地图和已落地架构说明，提交验收记录。

实现完成后更新本文当前状态和证据，不把尚未运行的真实平台压测写成通过。不需要另起新的“current”交接入口。

## 7. 验收矩阵：我们的验收重点

### 7.1 必须自动验证（合成数据、临时数据库、临时媒体）

建议新增 `backend/tests/test_task_store.py`、`test_task_runner.py`、`test_task_api.py`；按改动扩展已有 `test_asr_service.py`、`test_library_service.py`、`test_douyin_service.py`、`test_url_normalization.py` 等。前端 helper 测试放现有 `frontend/lib/*.test.ts` 目录模式。

| 场景 | 通过标准 |
| --- | --- |
| 一次 30 条，以及边界 49/50 条 | 30/49 正常接纳；50 明确拒绝且无部分入库；前端可纠正输入 |
| 并发提交、多标签页、同 key 网络重试 | 一个意图只有一个批次；活跃总量不超过 49 |
| 同内容短/长链接，不同 B 站分 P | 同一内容下游只执行一次；不同分 P 不误去重 |
| A 识别、B 下载、C 校对 | 使用事件/屏障证明时间区间重叠；不是只测试状态文字 |
| 49 条持续队列 | 浏览器≤1、下载≤2、识别≤1、DeepSeek HTTP≤2；预下载缓冲有界 |
| 单条+批量+手动下载+封面补取混合 | 所有真实入口共用浏览器限制，无独立绕行 |
| 第 3 条解析失败 | 第 4～30 条仍执行；只重试第 3 条，不重做其他完成结果 |
| 下载后、识别后、总结保存后重启 | 已保存阶段不重做；只有正在执行且无检查点的阶段重跑 |
| AI 请求结果不明时重启 | 停在可见的不确定失败，未经用户重试不重复付费请求 |
| 断网页/刷新/断网重连 | 后端完成接续；重新进入能回读任务与结果，不再次提交 |
| 入库失败、busy、记录缺失 | 不报告完成；可复用检查点重试保存，不自动重跑 AI |
| 摘录编辑与后台总结同时保存 | 两者都保留；旧文本总结不能覆盖新转写对应状态 |
| 领取与取消/重试同时发生 | 不双执行、不写入迟到旧结果、不误删已生成内容 |
| 两批次引用同一任务，其中一批取消 | 当前批次显示取消，另一批仍得到结果；全局只执行一份 |
| 活跃任务期间删除/清库 | 后端明确拒绝，任务完成后可按现有流程删除 |
| 原始稿存在、校对或总结失败 | 重试相应阶段不重复 ASR；降级状态真实可见 |
| 媒体失效、残留 .part、空间不足 | 刷新源有次数上限，残留不当成功，失败不阻断无关任务 |
| 额度耗尽 | 明确等待时间、不占资源、不忙重试，恢复后续跑 |
| 两个执行进程/应用关闭 | 只有一个有权调度；退出不遗留占 Profile 的本项目子进程 |

调度测试使用可注入时钟、可控 fake 下载/识别/AI 及执行计数，不靠长 sleep 或真实视频凑用例。mock E2E 覆盖批量提交、部分失败、重试、刷新恢复、回看结果，复用 `frontend/e2e/desktop.spec.ts` 的 mock 与浏览器错误捕获。
